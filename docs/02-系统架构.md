# 02 · 系统架构

## 1. 分层视图

```
┌─────────────────────────────────────────────────────────────┐
│  Presentation  (Flutter Widgets / Router / Theme)           │
│  首页 · 搜索 · 详情 · 播放器 · 直播 · 我的 · 插件 · 设置      │
├─────────────────────────────────────────────────────────────┤
│  Application   (Riverpod Providers / UseCase)               │
│  聚合搜索 · 播放编排 · 续播恢复 · 下载调度 · 插件管理          │
├─────────────────────────────────────────────────────────────┤
│  Domain        (纯 Dart，无框架依赖)                          │
│  Entity: MediaItem/Episode/PlaySource/Channel/SourceSite     │
│  Repository 接口 · 领域服务 · 错误类型                        │
├─────────────────────────────────────────────────────────────┤
│  Infrastructure                                             │
│  ┌────────────┬───────────────┬──────────┬───────────────┐  │
│  │ SpiderHost │ PlayerEngine  │ Storage  │ Net / Update  │  │
│  │ (进程管理  │ (libmpv 抽象) │ (drift)  │ (Dio/DoH)     │  │
│  │  + RPC)    │               │          │               │  │
│  └────────────┴───────────────┴──────────┴───────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

依赖方向严格向下：Presentation → Application → Domain ← Infrastructure。
Domain 不依赖任何外部包；Infrastructure 实现 Domain 定义的 Repository 接口。

## 2. 进程模型

这是 MiStream 与 TVBox 系客户端最本质的架构差异。

```
                     ┌──────────────────────────┐
                     │   mistream.exe (主进程)   │
                     │   Flutter UI + Core       │
                     │   libmpv (进程内 FFI)     │
                     └────┬─────────┬────────┬───┘
              JSON-RPC/   │         │        │  JSON-RPC/stdio
              stdio       │         │        │
        ┌─────────────────▼──┐  ┌───▼──────┐ │ ┌──────────────────┐
        │ spider-js          │  │ spider-  │ │ │ sniffer          │
        │ (QuickJS 沙箱)      │  │ python   │ │ │ (无头浏览器/CDP) │
        │ 每源一实例或池化     │  │ (CPython)│ │ │                  │
        └────────────────────┘  └──────────┘ │ └──────────────────┘
                                              │
                                    ┌─────────▼──────────┐
                                    │ spider-jvm (可选)   │
                                    │ JRE + android 兼容层│
                                    └────────────────────┘
```

**为什么 libmpv 在主进程内而 Spider 在进程外**：

- libmpv 是成熟的 C 库，崩溃率低，且视频渲染需要与 Flutter 的 GPU 纹理共享，跨进程代价过高。
- Spider 执行的是**用户导入的、不受信任的第三方脚本**，必须假设它会死循环、爆内存、崩溃、越权访问文件。

**子进程职责**：

| 进程 | 语言/运行时 | 生命周期 | 崩溃影响 |
| --- | --- | --- | --- |
| `spider-js` | Dart + QuickJS | 常驻，空闲 N 分钟回收 | 该源不可用，自动重启 |
| `spider-python` | CPython 嵌入 | 按需拉起 | 同上 |
| `spider-jvm` | JRE + shim | 按需拉起（可选组件） | 同上 |
| `sniffer` | WebView2 / CEF | 按需拉起，用完即杀 | 嗅探失败，回退解析链 |

HTTP 类型的 Spider 不需要子进程——它只是远端 HTTP 服务，由主进程直接 Dio 调用。

## 3. 关键数据流

### 3.1 聚合搜索

```
UI 输入关键词
  → SearchUseCase 从 SourceRepository 取出「已启用且 searchable」的站点列表
  → 按 sourceId 分组，向 SpiderHost 并发下发 search 请求
     · 全局并发上限（默认 8），单源超时（默认 8s）
     · 任一源失败/超时 → 记录错误，不阻塞其它源
  → 结果流式回灌 UI（StreamProvider），先到先显示
  → 按标题归一化去重、按源优先级排序
```

流式而非等待全部返回，是搜索体验的关键：主流配置动辄几十个源，等齐必然超时。

### 3.2 起播链路

```
用户点击某一集
  → PlayUseCase 调 Spider.playerContent(flag, id, vipFlags)
  → 返回三种形态之一：
     a) 直链 (parse=0)            → 直接交给 PlayerEngine
     b) 需解析 (parse=1)          → 走 parses 解析链，逐个尝试
     c) 网页地址                   → 拉起 sniffer 子进程嗅探媒体流
  → 得到最终 URL + headers(UA/Referer/Cookie)
  → PlayerEngine.open(url, headers, startPosition)
  → 起播成功 → 写 history；失败 → 按回退策略换下一个 flag / 解析器
```

失败回退顺序是明确的：**当前解析器 → 下一个解析器 → 嗅探 → 换播放线路(flag) → 报错**。

### 3.3 配置导入

```
用户粘贴 URL / 选择本地文件
  → ConfigFetcher 拉取原始字节
  → ConfigDecoder 依次尝试：明文 JSON → Base64 → AES 加密体
  → TvBoxConfigParser 解析为中间模型
  → 映射为 MiStream 领域模型（SourceSite / LiveGroup / ParseRule / SnifferRule）
  → 校验（必填字段、type 合法性、URL 协议白名单）
  → 落库 + 下载 spider jar/js 依赖到插件目录（带 md5 校验）
```

## 4. 模块清单

| 模块 | 职责 | 所在层 |
| --- | --- | --- |
| `core_domain` | 实体、值对象、Repository 接口、`Result` 与错误码 | Domain |
| `core_logging` | 结构化日志：JSONL 落盘、滚动与保留、脱敏 | Infrastructure |

| `spider_host` | 子进程生命周期、进程池、RPC 客户端、超时熔断 | Infrastructure |
| `spider_js` | QuickJS 运行时进程 + drpy 宿主 API | 独立可执行 |
| `spider_python` | CPython 运行时进程 | 独立可执行 |
| `spider_jvm` | JVM 运行时进程 + android 兼容层（可选） | 独立可执行 |
| `sniffer` | 无头浏览器嗅探进程 | 独立可执行 |
| `player_engine` | libmpv 抽象、事件流、轨道/字幕管理 | Infrastructure |
| `storage` | drift 数据库、迁移、DAO、缓存 | Infrastructure |
| `plugin_host` | Manifest 解析、权限、安装/更新/回滚 | Infrastructure |
| `theme_engine` | 设计令牌、主题包加载 | Infrastructure |
| `updater` | 版本检查、增量下载、校验、重启替换 | Infrastructure |
| `app` | UI、路由、Provider 装配 | Presentation/Application |

## 6. 关键架构决策（ADR 摘要）

| 编号 | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-001 | Spider 跑在独立子进程 | 进程内 Isolate | Isolate 无法隔离原生崩溃与内存爆炸；子进程可限权、可杀 |
| ADR-002 | 进程间用 JSON-RPC over stdio | gRPC / 本地 socket | stdio 零端口占用、零防火墙弹窗、跨平台一致 |
| ADR-003 | libmpv 在主进程内通过 FFI | 独立播放进程 | 渲染需共享 GPU 纹理，跨进程延迟与复杂度不可接受 |
| ADR-004 | 播放器先用 media_kit，保留 `PlayerEngine` 抽象 | 一开始就自研 FFI | 先打通端到端；抽象层保证后续可无损替换 |
| ADR-005 | 嗅探用独立无头浏览器进程 + CDP | 应用内嵌 WebView | 内嵌 WebView 会把第三方页面 JS 拉进主进程生命周期 |
| ADR-006 | Jar 运行时降级为可选组件 | 作为一等公民 | 依赖 JRE + Dex 转换 + android 兼容层，风险与收益不匹配 |
| ADR-007 | 状态管理用 Riverpod | Bloc / GetX | 编译期安全、易测试、无 BuildContext 依赖 |
| ADR-008 | 数据层用 drift | sqflite / ObjectBox | 类型安全 SQL、迁移工具链成熟、支持桌面 |

ADR 正文按 `docs/adr/NNN-*.md` 单独存放，格式见 [10-开发规范](10-开发规范.md)。

## 7. 跨平台差异点

| 能力 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| libmpv | 随包分发 dll | 随包 dylib / brew | 优先系统库，回退随包 |
| 硬解 | d3d11va | videotoolbox | vaapi / nvdec |
| 嗅探内核 | WebView2 (系统组件) | WKWebView | CEF 随包（体积代价大） |
| 自动更新 | 静默替换 + 重启 | Sparkle 风格 / DMG | AppImage / 包管理器交给发行版 |
| 安装形态 | MSIX + 便携 zip | .app/DMG | AppImage + tar.gz |

跨平台差异全部收敛在 `PlatformCapabilities` 抽象后面，上层不做 `if (Platform.isWindows)`。
