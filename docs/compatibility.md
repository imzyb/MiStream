# 版本兼容矩阵

MiStream 有四条**独立演进**的版本线。它们各自有自己的兼容规则，不能混为一谈。

| 版本线 | 载体 | 谁在消费 |
| --- | --- | --- |
| `appVersion` | SemVer，如 `1.2.3` | 用户、更新 feed |
| `protocolVersion` | 整数，如 `1` | RPC 双方（Host ↔ Runtime） |
| `manifestVersion` | 整数，如 `1` | 插件系统 |
| `schemaVersion` | 整数，如 `7` | 数据库迁移 |

把它们混成一个版本号，会导致「改个数据库字段就要发大版本」或者「协议破坏性变更被埋在小版本里」——两种都是灾难。

---

## 1. appVersion（应用版本）

SemVer，规则见 [10-开发规范](10-开发规范.md) §6.1。

**升 MAJOR 的充分条件**（满足任一）：

- `protocolVersion` 升级（老运行时不再兼容）
- `manifestVersion` 升级且不向后兼容（老插件不再可装）
- 数据库迁移不可逆，且降级会丢数据
- 移除了已公开承诺的能力

---

## 2. protocolVersion（RPC 协议）

见 [08-RPC协议](08-RPC协议.md) §8。

### 兼容规则

| 变更类型 | 是否升 `protocolVersion` | 协商方式 |
| --- | --- | --- |
| 新增方法 | 否 | `features` 数组协商 |
| 新增可选字段 | 否 | 接收方忽略未知字段 |
| 新增错误码 | 否 | 接收方按码段归类处理未知码 |
| 字段改名 / 改类型 | **是** | 无法协商，直接失败 |
| 移除方法 / 必填字段 | **是** | 同上 |
| 分帧格式变更 | **是** | 同上 |

**关键约束**：`protocolVersion` 不一致时**直接失败**（`PROTOCOL_VERSION_MISMATCH`），不做降级兼容。理由：运行时是随应用分发的，版本天然一致；只有用户手动替换运行时二进制时才会不一致，那种情况应该报错而不是静默降级。

### 矩阵

| protocolVersion | 引入于 | 状态 | 破坏性变更 |
| --- | --- | --- | --- |
| 1 | v0.1 | 当前 | — |

### features 位

新增能力用 `features` 协商，不动 `protocolVersion`：

| feature | 含义 | 引入于 |
| --- | --- | --- |
| `cancel` | 支持 `$/cancelRequest` | v0.1 |
| `storage` | 支持 `host.storage.*` | v0.1 |
| `progress` | 支持 `runtime.progress` 通知 | v0.1 |
| `sniff` | 支持 `host.sniff` | v0.5 |
| `gbk` | 支持 GBK 解码 | v0.1 |

Host 不得调用不在 `features` 交集里的能力——这是编译期无法保证的，必须有运行时断言。

---

## 3. manifestVersion（插件清单）

见 [06-插件系统](06-插件系统.md) §3。

### 兼容规则

| 变更类型 | 是否升 `manifestVersion` |
| --- | --- |
| 新增可选字段 | 否 |
| 新增权限类型 | 否（老插件不声明即不授予） |
| 新增贡献点 | 否 |
| 新增必填字段 | **是** |
| 改变已有字段语义 | **是** |
| 移除字段 | **是** |

### 双向约束

插件与应用的兼容由两侧共同声明：

- 插件侧：`engine.minAppVersion` / `engine.maxAppVersion`
- 应用侧：支持的 `manifestVersion` 范围

安装时两个条件都满足才允许。任一不满足，给出**明确的原因**（「此插件需要 MiStream 1.2.0 或更高版本，当前 1.0.0」），而不是笼统的「安装失败」。

### 矩阵

| manifestVersion | 支持的 appVersion | 状态 |
| --- | --- | --- |
| 1 | ≥ 1.0.0 | 当前 |

**弃用策略**：老 `manifestVersion` 至少支持 **2 个 MINOR 版本周期**后才可移除，且移除前一个版本必须在插件详情页显示弃用警告。

---

## 4. schemaVersion（数据库）

见 [07-数据库设计](07-数据库设计.md) §4。

### 规则

- 单调递增整数，**每次改表必须 +1 并写迁移**
- CI 必须验证 `v(N-1)→v(N)` 与 `v1→v(N)` 两条路径
- 迁移前自动备份，失败回滚且**拒绝启动**（宁可不启动，也不带着半迁移的库跑）
- **不支持降级**。用户从新版本回退到旧版本时，旧版本检测到 `schemaVersion` 高于自己支持的，拒绝启动并提示「请使用 1.x 或更高版本，或从备份恢复」

### 可重建数据

以下表在迁移时允许直接清空，不必费力搬运：

- `site_cache`（缓存，可重新拉取）
- `app_event`（诊断日志）
- `site` 的运行时状态列（`status` / `fail_count` / `last_ok_at` / `last_error` / `last_latency_ms`）

### 矩阵

| schemaVersion | 引入于 | 变更 |
| --- | --- | --- |
| 1 | v0.1 | 初始 schema |

## 5. 备份文件兼容

`.mistream-backup` 内含 `manifest.json`，其中记录 `backupVersion` 与导出时的 `appVersion`。

- 导入时若 `backupVersion` 高于当前支持 → 拒绝并提示升级应用
- 低于当前支持 → 按字段映射升级后导入，缺失字段取默认值
- 备份格式**必须向后兼容至少 1 个 MAJOR 版本**——用户的备份可能放了两年才拿出来用

---

## 6. 破坏性变更流程

任何一条版本线的破坏性变更，都必须走完整流程：

1. 开 issue 说明必要性，评估是否有非破坏性替代方案
2. 提 ADR（若涉及架构）
3. 更新本文件的对应矩阵
4. 在 CHANGELOG 中用 `BREAKING CHANGE` 明确标注
5. 若影响插件生态，提前一个 MINOR 版本发布弃用警告
6. 在发布说明中给出**具体的迁移指引**，不是「请更新插件」这种空话

**默认答案是不做破坏性变更。** 每一次都要先证明非破坏性方案确实不可行。
