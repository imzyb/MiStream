# 10 · 开发规范

## 1. 仓库与分支

Monorepo（melos 管理），目录结构见 [02-系统架构](02-系统架构.md) §5。

### 分支模型：trunk-based + release 分支

```
main ──────●────────●────────●────────●──────  （始终可发布，受保护）
            \        \                 \
             feat/x   fix/y             release/v1.0 ──● tag v1.0.0
                                                        \
                                                         hotfix/v1.0.1
```

- `main`：受保护，禁止直推，必须 PR + CI 全绿 + 至少 1 个 review。
- `feat/*` `fix/*` `chore/*` `docs/*` `refactor/*`：短生命周期（目标 < 3 天），从 `main` 切出，squash 合回。
- `release/vX.Y`：发布前从 `main` 切出，只接受 bugfix，打 tag 后合回 `main`。
- `hotfix/vX.Y.Z`：从 release tag 切出，修完同时合回 `release/*` 与 `main`。

不用完整 Git Flow 的 `develop` 分支——单/小团队下它只带来同步成本，不带来收益。

## 2. 提交规范

Conventional Commits，由 `tools/commit_lint` 在本地 hook（`.githooks/commit-msg`）
与 CI 的 `commitlint` job 双重校验，两处共用同一份实现。

自研而不用 npm 的 commitlint：这个仓库是纯 Dart/Flutter，为了校验提交信息
引入一整棵 node_modules（外加 package-lock、dependabot 的第二个生态、每个 CI
job 里装 Node）不划算；而 type/scope 白名单与「subject 用中文」这类项目约定
本来就要自己配，用现成工具也省不掉。

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type**：`feat` `fix` `perf` `refactor` `docs` `test` `build` `ci` `chore` `revert`

**scope**（对应模块，见架构文档）：`player` `spider` `spider-js` `rpc` `storage` `plugin` `theme` `ui` `config` `updater` `sniffer` `sdk` `domain` `logging` `tools` `ci` `deps`

scope 可以整个省略（例如 `docs: 补充里程碑出口标准` 这种覆盖全仓库的改动），
但写了就必须在白名单内。新增 scope 先改本节，再改
`tools/commit_lint` 的 `CommitLinter.defaultScopes`——反过来改会让文档失去
「单一事实来源」的地位。

**规则**：

- subject 用祈使句，中文英文均可但项目内保持一致（本项目：**中文**），不超过 50 字符，结尾无句号
- Breaking change 在 footer 写 `BREAKING CHANGE: <说明>`，或在 type 后加 `!`
- 关联 issue 写 `Closes #123`

示例：

```
feat(spider-js): 实现 pdfh 选择器的 &&Text 与 &&Html 语义

补齐 drpy 兼容层中最常用的两种取值方式，并加入 12 条回归用例。

Closes #45
```

## 3. 代码规范

### 3.1 静态检查

- `very_good_analysis` 作为基线 lint 规则集，`analysis_options.yaml` 放仓库根，各包继承。
- 分析器从被分析文件向上找最近的配置，所以子包**不写**自己的 `analysis_options.yaml` 即自动继承根配置。规则分散在十几个文件里必然漂移。
- CI 中 `flutter analyze --fatal-infos --fatal-warnings`，**零告警才算通过**。
- 允许的例外必须写 `// ignore: rule_name — 原因`，无原因的 ignore 视为错误（由 `tools/arch_check` 的 `ignore-reason` 规则强制）。
- `dart format` 在 pre-commit 自动执行（`.githooks/pre-commit`），CI 校验格式一致性。

### 3.2 命名

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 文件 | snake_case | `spider_host.dart` |
| 类 / 枚举 | UpperCamelCase | `SpiderHost` |
| 变量 / 方法 | lowerCamelCase | `fetchDetail` |
| 常量 | lowerCamelCase（Dart 惯例） | `defaultTimeout` |
| 私有 | 前缀 `_` | `_client` |
| Provider | 名词 + `Provider` | `siteListProvider` |
| 布尔 | `is` / `has` / `can` / `should` 开头 | `isSearchable` |

### 3.3 分层纪律

由 `tools/arch_check` 强制，`melos run check:arch` 与 CI 的 `arch` job 都跑它。
写在文档里的纪律会漂移——加一行 `import 'dart:io'` 只要一秒，而它一旦进去，
`core_domain` 就再也无法在纯 Dart 环境下跑测试，也无法被 `runtimes/` 下的子
进程复用。

- `core_domain` **不得** import Flutter、Dio、drift 或任何 IO 包。白名单式校验：`dart:` 只允许 `async` `collection` `convert` `math` `typed_data`，`package:` 只允许 `meta`；pubspec 依赖同样校验。
- Presentation 层不得直接调用 `spider_host` / `storage` / `plugin_host`，必须经 Application 层。
- 跨 feature 引用只能通过 `shared/` 或 Domain 层，禁止 `features/a` import `features/b/internal/*`。

### 3.4 错误处理

- 领域层用 `Result<T, AppError>`（sealed class）表达可预期失败，不用异常做控制流。
- 只有真正的编程错误（断言失败、非法状态）才 throw。
- 每个 `catch` 必须要么处理、要么转换为 `AppError` 上抛，**禁止裸 `catch (_) {}`**。
- 所有 `AppError` 带 `code`（对应 [08-RPC协议](08-RPC协议.md) §7 或本地错误码），UI 才能给出可读文案。

### 3.5 异步

- 禁止 `async` 方法中不 await 的 Future（lint 已覆盖 `unawaited_futures`）。
- 所有网络与 RPC 调用必须传超时。
- 所有可取消的长任务接受 `CancellationToken`，UI 离开页面时取消。

## 4. 测试策略

| 层次 | 范围 | 工具 | 门槛 |
| --- | --- | --- | --- |
| 单元测试 | Domain 逻辑、解析器、配置解码、错误映射 | `test` + `mocktail` | 核心包行覆盖率 ≥ 70% |
| 契约测试 | `PlayerEngine` 多实现、`SpiderRuntime` 多实现跑同一套用例 | `test` | 每新增实现必须通过 |
| 兼容性测试 | drpy 宿主 API：`(HTML 快照, 规则, 期望值)` 三元组 | 自建 harness | 只增不减，回归必跑 |
| Widget 测试 | 关键组件的四态渲染 | `flutter_test` | 每个共享组件至少一例 |
| 黄金测试 | 主题、卡片、播放器控制栏的视觉回归 | `golden_toolkit` | 仅在 Linux CI runner 上比对，避免字体差异 |
| 集成测试 | 端到端：导入配置 → 搜索 → 详情 → 起播 | `integration_test` + 本地 mock 源服务 | 每次 release 分支必跑 |
| 迁移测试 | v(N-1)→v(N)、v1→v(N) | drift migration 工具 | 每次改 schema 必加 |
| 沙箱逃逸测试 | 越权网络、SSRF、路径穿越、配额 | 自建 | 全部必须被拦截 |

**测试专用的 mock 源服务**：`tools/mock_source_server/`，一个本地 HTTP 服务，提供可控的正常/慢/错误/畸形返回。集成测试不依赖真实外部源——外部源不稳定，会让 CI 变成噪音源。

覆盖率不追求绝对数字，但以下路径必须有测试：配置解码链、`pdfh` 语义、播放回退编排、插件生命周期状态机、RPC 分帧、数据库迁移。

## 5. CI/CD

### 5.1 流水线

```
PR 触发：
  ├─ lint        （format 检查 + analyze --fatal-infos）        ← M0 已落地
  ├─ commitlint  （提交信息规范）                                ← M0 已落地
  ├─ arch        （分层纪律，tools/arch_check）                  ← M0 已落地
  ├─ test        （单测 + 契约 + 兼容性 + 迁移，矩阵 windows/macos/ubuntu）← M0 已落地
  ├─ build-check （三平台 debug 构建能过）                        ← M0 已落地
  ├─ license     （依赖 license 扫描，禁 AGPL/SSPL）              ← M10
  └─ golden      （仅 ubuntu）                                   ← M5

main 合入触发：
  └─ 上述全部 + nightly 产物上传（不发布）

tag v* 触发：
  ├─ build-release  （三平台 release 构建）
  ├─ sign           （Windows 代码签名 / macOS 公证）
  ├─ package        （MSIX + zip / DMG / AppImage + tar.gz）
  ├─ checksum       （生成 SHA256SUMS）
  ├─ changelog      （从 Conventional Commits 生成）
  ├─ github-release （草稿，人工确认后发布）
  └─ update-feed    （更新 latest.json）
```

`tag v*` 的整条流水线在 M10 落地。Flutter 版本由 `.tool-versions` 与 CI 的
`FLUTTER_VERSION` 共同锁定，见 [03-技术选型](03-技术选型.md) §2。

### 5.2 合并要求

- 全部检查通过
- 至少 1 个 approve（单人项目时可用 self-review checklist 替代，但不得跳过 CI）
- 无 `WIP` 标记，无未解决 conversation
- 涉及 schema / 协议 / 权限的变更必须同步更新 `docs/`，否则不予合并

### 5.3 构建产物

| 平台 | 产物 |
| --- | --- |
| Windows | `MiStream-{ver}-x64.msix`、`MiStream-{ver}-x64-portable.zip` |
| macOS | `MiStream-{ver}-universal.dmg` |
| Linux | `MiStream-{ver}-x86_64.AppImage`、`.tar.gz` |
| 通用 | `SHA256SUMS`、`SHA256SUMS.asc` |

## 6. 版本与发布

### 6.1 版本号

SemVer：`MAJOR.MINOR.PATCH`。

- MAJOR：数据库不兼容迁移、RPC `protocolVersion` 升级、插件 manifest 破坏性变更
- MINOR：新功能，向后兼容
- PATCH：仅修复

预发布：`1.0.0-beta.1`、`1.0.0-rc.1`。

**协议版本与应用版本独立**：`manifestVersion`、`protocolVersion`、`schemaVersion` 各自演进，各自有兼容矩阵，写在 `docs/compatibility.md`。

### 6.2 发布检查清单

发布前必须逐项确认（`docs/checklists/release.md`）：

- [ ] CHANGELOG 已生成并人工润色
- [ ] 版本号在 `pubspec.yaml`、安装包元数据、About 页一致
- [ ] 数据库迁移已测试（从上一个 release 版本的库升级）
- [ ] 播放矩阵手工回归（H.264/HEVC/AV1/HDR/ASS 字幕/多音轨）
- [ ] 兼容性测试集全绿
- [ ] 自动更新从上一版本升级验证通过（含回滚）
- [ ] 三平台安装包能正常安装/卸载，不残留
- [ ] 安装包内**确认不含任何源配置**（合规检查，脚本自动扫描）
- [ ] 开源许可证清单已更新（含 libmpv/ffmpeg 完整文本）

### 6.3 自动更新

- 静态 JSON feed：`https://<host>/update/{channel}/latest.json`
- 渠道：`stable` / `beta`，用户可选
- 流程：检查 → 显示 changelog → 用户确认 → 后台下载 → 校验 SHA256 与签名 → 下次启动时替换 → 失败自动回滚
- 关键约束：**永不静默更新**，永远给用户「稍后」选项；下载失败不影响当前版本使用

## 7. 依赖管理

- 生产依赖新增需在 PR 说明中回答：为什么必要、有无更轻量替代、license 是什么、维护状态如何。
- 锁定 `pubspec.lock` 并提交。
- `dependabot` 每周开升级 PR；MAJOR 升级单独开 issue 评估。
- 原生二进制依赖（libmpv、CEF）锁定版本 + hash 校验，构建脚本中验证。
- 定期（每季度）跑一次依赖安全扫描。

## 8. 文档纪律

- `docs/` 是设计的**单一事实来源**。代码与文档冲突时，先改文档达成共识再改代码。
- 架构决策写 ADR：`docs/adr/NNN-短标题.md`，格式为「背景 / 决策 / 备选方案 / 后果 / 状态」。状态为 `提议 / 已接受 / 已废弃 / 被 ADR-XXX 取代`。
- 以下变更**必须**同步改文档：数据库 schema、RPC 方法或错误码、插件 manifest、Spider 接口、设计令牌。
- 每个 `packages/*` 有自己的 README，说明职责、公共 API、如何单独测试。
- 面向源作者的文档单独维护在 `sdk/` 下，与内部设计文档分离。

## 9. 日志与诊断

实现在 `packages/core_logging`。

- 结构化日志，JSONL 落盘：`logs/app-{date}.jsonl`，保留 7 天，单文件上限 20MB 后滚动。
- 滚动用**换文件**（`app-{date}.1.jsonl`）而非改名：Windows 上重命名已打开的文件会失败。
- 字段：

  | 字段 | 类型 | 说明 |
  | --- | --- | --- |
  | `ts` | string | ISO 8601，统一 UTC |
  | `level` | string | `trace` / `debug` / `info` / `warn` / `error` / `fatal` |
  | `scope` | string | 模块名 |
  | `siteId` | string? | 相关源站点，诊断面板按它过滤 |
  | `code` | int? | 错误码数值（见 [08-RPC协议](08-RPC协议.md) §7）|
  | `codeName` | string? | 错误码常量名，如 `SCRIPT_TIMEOUT` |
  | `message` | string | 人可读说明 |
  | `detail` | object? | 结构化补充信息 |
  | `error` | string? | 原始异常 |
  | `stack` | string? | 原始堆栈 |

  `code` 与 `codeName` 同时落盘：前者给日志处理工具按数值过滤，后者给人读——
  贴进 issue 的诊断信息里，`SCRIPT_TIMEOUT` 比 `-32102` 有用得多。
- 级别默认 `info`，可在设置中调到 `debug`（会提示影响性能）。
- **日志脱敏**：URL 的 query string 中的 token/key 字段、Cookie、Authorization 头一律打码。这是硬要求，实现上做成**结构性不可绕过**：`LogRecord` 没有无参 `toJson()`，序列化必须交出一个 `Redactor`，而 `Redactor` 没有「关闭」模式。于是「忘了脱敏」在类型层面就写不出来，不需要靠 CI grep 去抓。
- 敏感词表分两份：URL query 里的裸 `key` 要打码（几乎一定是 API key），但结构化字段里的 `key` 不打（TVBox 配置里它是站点标识 `{"key":"csp_XXX"}`，打掉诊断就没法看了）。
- 「复制诊断信息」按钮生成的报告包含：版本、平台、最近 50 条相关日志、源状态——脱敏后可直接贴到 issue。最近 N 条由 `MemoryLogSink` 的环形缓冲提供。

## 10. 安全基线

| 项 | 要求 |
| --- | --- |
| 网络 | 所有外部请求经统一网络层；证书校验不得关闭；不信任任何源返回的重定向到私网地址 |
| SSRF | 私网/回环/链路本地地址一律拦截（含重定向后的地址） |
| 路径 | 所有来自配置/插件的路径做规范化 + 前缀校验，防 `../` 逃逸 |
| 反序列化 | 所有外部 JSON 经 schema 校验后才映射为领域对象 |
| 密钥 | 不在代码中硬编码任何密钥；签名私钥只存在 CI secrets |
| 遥测 | 默认全关。开启需用户显式同意，且明确列出上报内容 |
| 依赖 | 禁止引入需要网络下载脚本执行的构建步骤 |

## 11. 贡献流程

1. 开 issue 描述问题或提案（模板：bug / feature / source-compat）
2. 讨论达成方向共识（涉及架构则先提 ADR）
3. 切分支实现 + 补测试 + 更文档
4. 提 PR，模板中勾选自检项
5. Review → 修改 → squash 合并
6. 关联 issue 自动关闭

**源兼容性问题**单独用 `source-compat` 模板，要求提供：源类型、最小复现规则、期望输出、实际输出、脱敏后的诊断信息。这类 issue 的修复必须附带一条兼容性测试用例。
