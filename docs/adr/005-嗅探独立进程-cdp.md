# ADR-005：嗅探用独立无头浏览器进程 + CDP

**状态**：已接受

## 背景

部分数据源不返回直链，而是给出一个网页地址，真实媒体流藏在页面 JS 执行后发起的网络请求里。要拿到它，必须真的加载并执行这个页面。

这带来一个尖锐的问题：**我们要在自己的应用里执行任意第三方网页的 JavaScript**。这些页面通常还带着广告脚本、追踪器、反调试逻辑，甚至可能是恶意的。

TVBox 的做法是用 Android 系统 WebView 在应用内嗅探。桌面端如果照搬，等于把不可信页面拉进主进程生命周期——与 [ADR-001](001-spider-独立子进程.md) 的隔离原则直接冲突。

## 决策

我们将用**独立的无头浏览器子进程**执行嗅探，通过 **Chrome DevTools Protocol (CDP)** 驱动和监听。

- 进程内核按平台选择：Windows 用 WebView2、macOS 用 WKWebView、Linux 随包 CEF
- 统一以 CDP 语义抽象，上层不感知内核差异
- 监听 `Network.requestWillBeSent` / `Network.responseReceived`，按扩展名与 Content-Type 匹配媒体流
- **用完即杀**：不复用 profile、不持久化 cookie、不保留缓存
- 嗅探永远是**最后手段**，排在解析器链之后（[04-播放器设计](../04-播放器设计.md) §7）

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| 应用内嵌 WebView | 实现最简单，交互体验好 | 第三方页面 JS 进入主进程生命周期；内存泄漏、崩溃、弹窗劫持全部直接影响应用；无法可靠清理状态 |
| 纯 HTTP 请求 + 正则匹配 | 无浏览器依赖，快，轻 | 对需要 JS 执行的页面完全无效——而这恰恰是需要嗅探的全部理由 |
| 内嵌轻量 JS 引擎模拟浏览器环境 | 无浏览器体积 | DOM、fetch、XHR、Worker、CSS 的模拟深度永远不够；现代页面的反爬检测能轻易识别；维护成本无底洞 |
| Puppeteer / Playwright sidecar | 生态成熟、API 好用 | 需要 Node.js 运行时 + 完整 Chromium 下载（数百 MB），严重超出体积预算；且引入 npm 依赖树 |
| 要求用户自行安装浏览器并远程调试 | 零体积成本 | 用户体验不可接受；且劫持用户日常浏览器的调试端口有安全问题 |

## 后果

**正面**

- 不可信页面的执行被完全隔离在一次性进程中，崩溃、泄漏、劫持都影响不到主进程
- 用完即杀保证了状态不累积，也避免了跨站追踪（页面无法通过 cookie 关联多次嗅探）
- CDP 是事实标准，抽象稳定，换内核不改上层
- 嗅探过程可开调试窗口观察，源作者能直接调规则

**负面**

- **平台内核不一致**是本决策最大的债：WebView2 的 CDP 支持与 Chromium 有差异，WKWebView 根本不原生支持 CDP（需要一层适配到 WebKit Inspector Protocol）
  - 缓解：CDP 抽象层只用最小共同子集（页面导航 + 网络事件），不依赖高级能力
- Linux 需要随包 CEF，体积 +100MB。因此 Linux 版嗅探做成**可选组件**，缺失时优雅降级并提示（`SNIFFER_UNAVAILABLE`）
- 进程启动开销大（数百毫秒到秒级），所以嗅探必须排在解析器链之后，不能作为首选路径
- 页面加载慢或反爬时嗅探会超时（默认 20s），这段时间用户在等待——UI 必须明确显示「正在嗅探」而不是无信息转圈
