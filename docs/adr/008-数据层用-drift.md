# ADR-008：数据层用 drift

**状态**：已接受

## 背景

MiStream 的本地数据有几个特点决定了选型：

- **关系明确**：`config_source → site → history/favorite/download` 是清晰的层级，有真实的外键约束需求
- **查询有复杂度**：按分组的收藏、按日期分组的历史、缓存的过期与 LRU 淘汰、解析器成功率统计排序，都不是简单 KV 取值
- **必须能迁移**：这是长期维护的桌面应用，用户数据（收藏、历史）丢了就是灾难性体验。schema 会持续演进（[07-数据库设计](../07-数据库设计.md) §4）
- **只有主进程写**：子进程不直连数据库，无并发写冲突（[07-数据库设计](../07-数据库设计.md) §1）
- **跨三桌面平台**

## 决策

我们将使用 **SQLite（`sqlite3_flutter_libs` 随包分发）+ drift** 作为数据层。

- schema 用 drift 的 Dart DSL 定义，生成类型安全的查询 API
- `MigrationStrategy` + schema 快照 + 迁移测试工具链，**每次改表必须写迁移**，禁止 `deleteDb` 重建
- CI 中验证 `v(N-1)→v(N)` 与 `v1→v(N)` 两条迁移路径
- 迁移前自动备份，失败则回滚并拒绝启动

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| sqflite / sqlite3 裸用 | 无生成代码，轻量，SQL 完全可控 | 手写 SQL 字符串无类型检查，字段改名只能在运行时炸；结果集到对象的映射要全部手写；迁移全靠自己搭框架 |
| Isar | 性能优秀，API 现代，无需 SQL | 迁移能力弱（历史上有过破坏性变更）；关系表达不如 SQL 自然；项目维护活跃度存在不确定性——对一个要存用户十年收藏的应用，这是不可接受的风险 |
| ObjectBox | 性能最好，跨平台 | 原生库依赖增加体积与构建复杂度；关系查询表达力不如 SQL；商业授权模型对开源项目有不确定性 |
| Hive / KV 存储 | 极简，无 schema 负担 | 无法表达关系与约束；复杂查询（分组、排序、聚合、LRU）要全部在内存里做，数据量大时不可行 |
| 文件 + JSON | 零依赖 | 无事务、无并发保护、无部分读取；历史记录上万条后每次读写全量文件不可接受 |

## 后果

**正面**

- **类型安全**：表结构改动会在编译期暴露所有受影响的查询，而不是等用户报 bug
- **迁移是一等公民**：drift 的迁移测试工具能验证任意版本对之间的升级路径，这直接对应风险登记册 R12（数据丢失）
- SQL 的表达力足够覆盖所有查询需求，不需要在应用层做数据处理
- SQLite 本身极其成熟稳定，是这类应用事实上的默认选择；数据文件可用任意 SQLite 工具检查，排障方便
- 外键 + `ON DELETE CASCADE` 让「删除配置源自动清理其下所有站点与关联数据」由数据库保证，不依赖应用逻辑正确

**负面**

- **生成代码量大**：每张表生成对应的 data class、companion、table 定义，构建时间与仓库体积都有可观增长
  - 缓解：生成代码不提交（`.gitignore`），CI 与本地都走 build_runner
- build_runner 是开发体验上的持续摩擦（改表后要重新生成，watch 模式占资源）
- drift 的 DSL 与原生 SQL 有学习成本，复杂查询有时需要退回 `customSelect`
- SQLite 单写者模型意味着如果将来需要子进程直接写库，架构要调整
  - 当前设计已明确子进程通过 RPC 回主进程写（[08-RPC协议](../08-RPC协议.md) §4），不构成问题
