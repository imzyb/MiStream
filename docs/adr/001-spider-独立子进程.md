# ADR-001：Spider 运行在独立子进程

**状态**：已接受

## 背景

Spider 执行的是**用户从互联网导入的、不受任何审计的第三方脚本或二进制**。它们会：

- 死循环（源作者写错正则、页面结构变了导致无限重试）
- 无节制申请内存（把整页 HTML 反复拼接）
- 抛出未捕获异常
- 尝试访问本地文件或内网地址（无论有意还是被上游污染）
- 在 Jar 形态下直接执行不可审计的原生逻辑

TVBox 系客户端把 Spider 跑在主进程里，因此「某个源挂了导致整个 App 崩溃/卡死」是该生态的常态问题。MiStream 的核心卖点之一就是不能重复这个问题。

约束：桌面平台，进程创建成本可接受（毫秒级）；用户可能同时启用几十个源。

## 决策

我们将把所有 Spider 运行时放在**独立子进程**中执行，主进程只通过 IPC 与之交互。

- 同类型运行时共用一个子进程，源之间用运行时内的 Context 隔离，进程数不随源数线性增长
- 主进程持有子进程的生杀权：超时可杀，内存超限可杀，崩溃自动重启
- 子进程不继承主进程句柄，工作目录限定在独立 sandbox 目录

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| Dart Isolate | 创建快、通信方便、无序列化跨进程开销 | **无法隔离原生崩溃**——QuickJS 或任何 FFI 层的段错误会带走整个进程；无法限制内存（Isolate 共享进程堆）；无法在 OS 层面限权 |
| 主进程内直接执行 | 最简单 | 完全没有隔离，正是要解决的问题 |
| WebAssembly 沙箱 | 隔离性好、跨平台一致 | drpy 生态是 JS 源码不是 wasm；把 QuickJS 编译进 wasm 再跑 JS，性能与调试复杂度都不可接受；Jar/Python 无法走这条路 |
| 容器/虚拟机 | 隔离最强 | 桌面客户端不能要求用户装 Docker；启动开销以秒计 |

## 后果

**正面**

- 源崩溃、死循环、OOM 全部被限制在子进程内，主进程与播放不受影响
- 可以在 OS 层面施加限制（Windows Job Object 限内存与子进程创建，未来可加 AppContainer / seccomp）
- 网络能力可以完全收回主进程（见 [ADR-002](002-json-rpc-over-stdio.md) 与 [05-Spider引擎](../05-Spider引擎.md) §4），子进程本身不需要网络权限
- 崩溃可观测：进程退出码与 stderr 是明确信号，不像进程内异常那样可能被吞掉

**负面**

- 引入了完整的 IPC 协议层，这是实打实的复杂度与工作量（分帧、背压、超时、取消、重连、版本协商）
- 每次调用有序列化与管道往返开销（实测目标：单次调用协议开销 < 2ms）
- 调试变难：需要专门的 RPC 录制/回放工具才能排查跨进程问题
- 打包变复杂：需要分发多个可执行文件，且要处理各平台的进程启动差异

这些负面后果是明知且接受的——它们是可控的工程成本，而进程内执行的风险是不可控的用户体验损失。
