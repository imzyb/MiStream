# ADR-004：播放器先用 media_kit，保留可替换的抽象层

**状态**：已接受

## 背景

[ADR-003](003-libmpv-进程内-ffi.md) 决定在主进程内用 FFI 调 libmpv。接下来的问题是：自己写 FFI 绑定，还是用现成封装？

现实情况：

- 「让视频画面出现在 Flutter widget 里」这一步涉及 mpv render API、GPU 纹理注册、三平台的纹理互操作，是整个播放器工作量中**最容易卡住数周**的部分
- `media_kit` 已经解决了这一步，且在多个 Flutter 桌面项目中被验证
- 但 media_kit 是一层封装，**不暴露全部 mpv 选项**——HDR tone-mapping 参数、自定义 shader（如 Anime4K）、精细的硬解回退控制、部分滤镜链，都在它的接口之外
- MiStream 的差异化卖点恰恰包含这些高级能力

风险：如果直接依赖 media_kit 的 API 写满整个 UI 层，将来想换实现就要重写 UI。

## 决策

我们将**分两期实现，并从第一行代码起就隔离在抽象层后面**：

1. 定义 `PlayerEngine` 抽象接口（[04-播放器设计](../04-播放器设计.md) §3），UI 与编排层只依赖它
2. 一期实现 `MediaKitEngine`，快速打通端到端（M1）
3. 二期实现 `NativeMpvEngine`，`dart:ffi` 直连 libmpv client API，解锁高级能力（M15）
4. 两个实现跑**同一套契约测试**——这是抽象层没有泄漏的唯一可验证证据

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| 一开始就自研 FFI 绑定 | 无中间层，能力完整 | 纹理共享这一步可能卡住数周，把关键路径（M0→M3→M4→M5）后移；MVP 迟迟出不来，全项目节奏受损 |
| 永远只用 media_kit | 省事 | 高级播放能力是产品差异化的核心，被上游封装限制住等于放弃卖点；且上游维护节奏不由我们控制 |
| 直接依赖 media_kit API，将来再重构 | 短期最快 | 「将来再重构」在实践中等于永远不重构；UI 层散落几百处 media_kit 调用后，替换成本会高到无法立项 |
| Fork media_kit 并自行扩展 | 复用已有成果 | 承担上游全部维护成本却拿不到上游更新；不如直接自研那一层薄的 FFI |

## 后果

**正面**

- M1 能快速交付可用的播放能力，不阻塞关键路径
- 抽象层强制我们**先想清楚播放器该暴露什么能力**，而不是被上游 API 形状牵着走
- 契约测试成为长期资产：将来任何新实现（比如某平台的特殊后端）都能用同一套用例验证
- 上游若停止维护，我们有明确的退出路径，不是被动等待

**负面**

- 抽象层本身有成本：一层转发、一套契约测试、以及「抽象是否合适」的持续判断
- 一期存在能力天花板：HDR tone-mapping、自定义 shader 在 M15 之前不可用。这些能力在 [04-播放器设计](../04-播放器设计.md) §4 中被标注为「尽力」或推迟，**不进 v1.0 出口标准**
- 有抽象泄漏的风险——如果 `PlayerEngine` 的接口设计不自觉地照抄了 media_kit 的形状，二期会发现接口不够用
  - 缓解：接口设计以 **mpv 的原生能力**为参照系，而不是以 media_kit 能提供什么为参照系
