# ADR-003：libmpv 在主进程内通过 FFI 调用

**状态**：已接受

## 背景

[ADR-001](001-spider-独立子进程.md) 把不可信代码推到了子进程。一个自然的追问是：播放器要不要也放进独立进程？

MPV 本身支持独立进程模式（`--input-ipc-server`），很多前端就是这么做的。但 MiStream 的约束不同：

- 视频画面必须渲染进 **Flutter 的 widget 树**中（要在上面叠加控制栏、字幕设置面板、剧集抽屉，且要跟随窗口布局与动画）
- 这要求视频帧以 **GPU 纹理**形式共享给 Flutter 的渲染管线
- 播放控制需要低延迟响应（seek、逐帧、音量），交互延迟直接被用户感知

libmpv 是成熟的 C 库，其崩溃风险与「用户导入的第三方脚本」不在同一个量级上。

## 决策

我们将在**主进程内**通过 `dart:ffi` 调用 libmpv（一期经由 media_kit 封装，见 [ADR-004](004-播放器分两期实现.md)），使用 mpv 的 render API 将视频帧渲染到与 Flutter 共享的 GPU 纹理上。

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| 独立 mpv 进程 + IPC 控制 | 崩溃隔离；可复用 mpv 的成熟 IPC | 跨进程 GPU 纹理共享在三平台上各有一套复杂机制（D3D11 shared handle / IOSurface / DMA-BUF），实现与维护成本极高；控制延迟增加；无法把视频自然嵌进 widget 树 |
| 独立进程 + 无边框窗口叠加 | 实现相对简单 | 窗口层级、缩放动画、圆角、遮罩全部失控；多显示器与 DPI 变化下的对齐问题无解；这是「看起来能用但处处别扭」的方案 |
| 自己用 ffmpeg 解码 + Flutter 绘制 | 完全可控 | 等于重写 mpv 的一半——音视频同步、字幕渲染、硬解回退、滤镜链，每一项都是多年工程量 |
| 用 Flutter 的平台视图（PlatformView）嵌原生播放器 | 各平台有现成播放器控件 | 平台视图在 Flutter 桌面端性能与合成表现较差；且各平台播放器能力差异大，违背「跨平台一致」目标 |

## 后果

**正面**

- 视频是 widget 树里的一等公民，布局、动画、层叠、圆角全部自然work
- 播放控制是进程内函数调用，延迟最低
- 只需维护一套渲染路径

**负面**

- **libmpv 崩溃会带走整个应用**。这是本决策接受的核心风险
  - 缓解 1：锁定 libmpv 版本并校验 hash，不随系统漂移（见 [03-技术选型](../03-技术选型.md) §2）
  - 缓解 2：硬解失败自动降级软解，避免驱动层崩溃（[04-播放器设计](../04-播放器设计.md) §5）
  - 缓解 3：播放前的所有不可信处理（源脚本、嗅探）都已在子进程完成，交给 libmpv 的只是一个 URL 和一组 header
  - 缓解 4：崩溃上报中单独统计播放器崩溃，作为质量门禁指标
- 引入 FFI 层，需要处理内存生命周期与线程亲和性（mpv 的 render context 有线程要求）
- libmpv 的 License 约束进入主进程边界，必须用 LGPL 构建产物 + 动态链接（见 [03-技术选型](../03-技术选型.md) §5）

**重新评估的触发条件**：若 beta 阶段播放器崩溃率持续高于 0.3%，重新评估独立播放进程方案。
