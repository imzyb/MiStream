# ADR-006：Jar 运行时降级为实验性可选组件

**状态**：已接受

## 背景

TVBox 生态中有相当数量的存量源以 jar 形态分发（`sites[].api` 形如 `csp_XXX`，从全局 `spider` jar 中加载类）。支持它们能直接继承一大批现成的源。

但把这些 jar 跑在桌面端，面对的是四个叠加的障碍：

1. **字节码格式不对**——多数产物是 Android 的 Dex 字节码，不是标准 JVM class。需要 dex→jar 转换，且转换结果不保证可运行。
2. **依赖 Android 框架 API**——大量 jar 直接调用 `android.util.Base64`、`android.text.TextUtils`、`android.content.Context`、`android.webkit.WebView`。桌面 JVM 上这些类根本不存在，必须写一层兼容 shim。
3. **依赖 WebView 执行 JS 挑战**——部分 jar 内部拉起 Android WebView 处理反爬，需要转接到我们的 sniffer 进程，语义无法完全对齐。
4. **闭源二进制，不可审计**——这是安全上最难接受的一点。用户无从判断一个 jar 到底做了什么。

同时，「四类运行时（JS/Jar/Python/HTTP）」已经出现在项目早期描述里，用户会形成预期。

## 决策

我们将把 Jar 运行时**降级为实验性可选组件**，并明确承诺边界：

- **不进 v1.0 出口标准**，排在 M15（v2.0 阶段）
- 做成可选组件：用户自行安装 JRE 17+，MiStream 提供 `spider_jvm` 进程与有限的 android 兼容 shim
- 只承诺「**纯 Java 逻辑 + 已 shim 的 android API 子集**」可运行，**不承诺任意 jar 可用**
- UI 中对 jar 源标注「实验性 · 二进制不可审计」，需用户显式确认后才加载
- 这条降级必须在 README、ROADMAP、UI 三处同时写明，避免预期错位

优先级排序确定为：JS (P0) > HTTP (P0) > Python (P2) > JVM (P3)。

## 备选方案

| 方案 | 优点 | 放弃原因 |
| --- | --- | --- |
| 作为一等公民完整支持 | 直接继承最多存量源 | 工作量与不确定性都极高（dex 转换 + android shim 覆盖率 + WebView 语义对齐），且**终点不可达**——永远会有 jar 用到没 shim 的 API。把它放在关键路径上会让 v1.0 无限期推迟 |
| 完全放弃 jar 支持 | 最省事，安全边界最清晰 | 放弃了一批用户的实际需求；且「四类运行时」的早期表述会变成失信 |
| 内置 JRE 随包分发 | 用户零配置 | 体积 +150MB 以上，严重超预算；且要承担 JRE 的安全更新责任 |
| 在服务端跑 jar，客户端只取结果 | 客户端零负担 | 与合规边界冲突（[01-项目概述](../01-项目概述.md) §6 不做服务端）；且需要我们运营基础设施 |
| 用 GraalVM / TeaVM 转译 | 理论上可消除 JVM 依赖 | 对反射与动态加载支持有限，而 jar spider 恰恰重度依赖反射；转译失败率高 |

## 后果

**正面**

- 关键路径（M0→M3→M4→M5）不被这个高不确定性的模块阻塞，v0.1 与 v1.0 可以按计划交付
- 资源集中投向 JS 运行时——那才是生态占比最高、投入产出比最好的方向
- 安全边界清晰：不可审计的二进制被隔离在「实验性 + 显式确认」的路径上，不是默认能力
- 承诺边界写清楚后，用户预期可管理，不会因为「某个 jar 跑不起来」而认为是产品缺陷

**负面**

- 一部分只有 jar 形态的源在 v1.0 前完全不可用，会流失这部分用户
- 「四类运行时」的表述需要在所有对外材料中修正为分级表述，早期看到旧描述的用户可能感到落差
- M15 真正实施时，android shim 的覆盖率仍是开放问题，可能需要长期持续补充
- 需要额外做「运行时缺失时源灰显 + 安装引导」的 UI 路径，否则用户只会看到一堆报错的源
